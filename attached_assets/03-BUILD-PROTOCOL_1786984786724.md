# 03 BUILD PROTOCOL

How work moves from spec to committed code. Seven slices, one at a time.

---

## The loop

1. Claude writes the Replit prompt for the current slice, using the format below.
2. Randy runs it in Replit.
3. Randy pulls to the local repo and brings the changed files to Claude.
4. Claude reviews against the acceptance criteria and the standing checks.
5. Defects go back to Replit as a correction prompt naming spec sections.
6. When the slice passes, Randy commits with the slice name in the message.
7. Next slice.

**Do not start a slice before the previous one is committed.** A half-finished slice underneath a new one turns every review into archaeology.

---

## Replit prompt format

Every prompt to Replit has these six parts, in this order. Nothing else.

```
CONTEXT
  One paragraph. What exists already, what this slice adds.

BUILD
  Numbered, specific, verifiable. Each item is one thing.

CONSTRAINTS
  Quoted spec rules that apply, with section numbers.
  Always include the standing constraints below.

FILES
  Where things go. Exact paths.

DONE WHEN
  The acceptance criteria, copied from this document.

DO NOT
  The specific wrong turns available on this slice.
```

**Quote the spec, do not summarize it.** Replit's agent follows quoted rules more reliably than paraphrased intent.

### Standing constraints, every prompt

```
- Plain CSS with custom properties. Do NOT use Tailwind, shadcn, or any
  CSS framework. The stylesheet is ported from vrtsync-crm-mockup.html.
- Do NOT redesign anything. The mockup is the approved design.
- Row vertical padding is 8px. Table cells 10px. Card headers 12px.
- Never use --accent as a text color. Use --accent-ink.
- No em dashes or en dashes anywhere, including comments and UI copy.
- Server is a JSON API only. No server-rendered pages.
- Do not add features, fields, routes, or screens not named in BUILD.
```

That last line matters more than it looks. Replit's agent is helpful by default and will add a settings page nobody asked for.

### Slice 4: Templates and the stage engine

**The one that matters.** Slow down here.

## Review protocol

Run in this order. Stop and report if step 1 fails.

**Step 1: Standing checks.** Every review, regardless of slice.

| Check | Spec |
|---|---|
| No Tailwind, no CSS framework in the dependency tree | 4.0 |
| `--accent` never used as a text color | 4.6 note A |
| Row padding 8px, cells 10px, card headers 12px | 3.8 |
| Task rows carry four facts, control leading, status trailing | 3.4 |
| No em dashes or en dashes, code and copy | 11 |
| Status never communicated by color alone | 12 |
| No raw hex outside the token block | 4 |

**Step 2: Acceptance criteria** for the slice, item by item. Each one passes or fails, no partial credit.

**Step 3: Spec sections** the slice cites, read and compared against the implementation.

**Step 4: Scope.** Did Replit add anything not in the prompt? Extra routes, extra tables, extra screens, a settings page, a notifications system. Name it and recommend removing it. Unrequested features are the most common way a small tool becomes Zoho again.

**Step 5: Structure.** Does this make the next slice harder? Logic in components that belongs in the API, a second timeline implementation, a hardcoded value that should be a token.

### Review output format

```
VERDICT: pass | pass with defects | fail

DEFECTS (violates spec, must fix)
  [§ref] file:line  what is wrong  what it should be

DRIFT (compliant but heading wrong)
  [§ref] what and why it matters

SCOPE ADDITIONS
  what Replit added that nobody asked for

PASSED
  the acceptance criteria that are genuinely done
```

The PASSED section is not padding. Randy needs to know what he can stop checking.

## Correction prompts

When sending defects back to Replit, one prompt per round, not one per defect. Format:

```
FIX
  Numbered, one per defect, each quoting the spec rule violated.

DO NOT
  Change anything not listed above.
  Refactor anything not listed above.
```

That second line is necessary. Given a correction, the agent will often improve nearby code it was not asked to touch, and the next review has to re-verify work that already passed.

---

## Commit discipline

One commit per passed slice, message naming the slice. Never commit a slice with open defects. If Replit produces something good and something broken in the same run, fix the broken part before committing rather than committing and fixing forward.

The repo is the rollback. It only works if every commit is a state you would be willing to return to.

---

## Seed data

Replit needs realistic data or you will review empty screens.

Seed from the mockup: six to eight communities spread across stages, four users covering all three roles, a handful of contacts per customer including one contractor, notes of every kind, and enough tasks to test the density floor on Team To-Do.

Seeds live in a script that can be rerun against a reset database. Do not hand-enter test data.
