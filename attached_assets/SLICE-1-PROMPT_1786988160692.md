CONTEXT

This is a new internal CRM for a property maintenance software company, replacing Zoho for a team of four to six. Nothing exists yet. This slice builds the foundation only: a Vite React single page client, an Express JSON API, Postgres with Drizzle, Google OAuth restricted to one Workspace domain, the users and customers tables, the application shell, and the stylesheet. The stylesheet is not written from scratch. It is lifted out of vrtsync-crm-mockup.html, which is in the repository root. That file is an already approved design covering all seven screens of the finished product. This slice renders only the shell. No screen content, no other tables, no other features.

This repository starts empty. Build the tree in FILES exactly as written, a plain /client and /server pair in JavaScript. If this workspace was scaffolded as a pnpm monorepo with an existing API server package, shared db or api-spec libraries, an artifacts directory, or a generated OpenAPI document, remove that scaffolding and do not map onto it. There is no OpenAPI contract layer in this project. Use the paths in FILES verbatim.

The specification has been amended since the mockup was made. Amendment A1 in 02-SPEC.md replaces the flat property profile with four service layers. Read A1 before creating the customers table. The layer table itself is not built in this slice.

BUILD

1. Scaffold a single repository with a Vite React client and an Express server. The server is a JSON API only. The client is a single page app that consumes it.
2. Provision Postgres and wire Drizzle ORM with a migration setup.
3. Open vrtsync-crm-mockup.html. Extract the entire contents of its style block into real CSS files under client/src/styles. Do not rewrite, reinterpret, or "improve" any value while extracting. Keep every component class name exactly as it appears in the mockup: .row, .deal, .pchip, .anchor, .k-alarm, .stepper, and all others.
4. Define the full token block in client/src/styles/tokens.css exactly as specified in CONSTRAINTS below: surfaces, chrome, text, lines, accent, status, rule gradients, the eight stage tokens, type, space, shape, shadow, breakpoints.
5. Apply these six cleanups during the extraction, not later:
   a. Stage colors currently appear as inline hex literals in the pipeline board column headers, the Pipeline by Stage list, and the anchor band legend, roughly 30 occurrences. Define the eight --stage-* tokens and reference them by name everywhere. No stage color remains a literal.
   b. Assorted raw hex in component CSS, mostly gradient stops, hover borders, and avatar colors. Promote to tokens, or leave a comment marking the value as an intentional one off.
   c. --sp-1, --bp-desktop, and --bp-tablet are defined but unused in the mockup. Use them or drop them.
   d. Three em dashes remain in CSS comments. Remove them.
   e. The mockup banner and the demo nav sub-item for a hardcoded customer are scaffolding. Drop both.
   f. Avatar colors are hardcoded per person as .av-rm and .av-dk. Replace with a function that derives a color deterministically from the user id, so the same user is the same color on every screen and the palette survives staff changes.
6. Drizzle schema, these two tables only:

   users
     id, google_sub (unique), email, name, avatar_url,
     role (sales|mapping|admin|owner|null), is_active, created_at

   customers
     id, name, management_company, is_self_managed, unit_count, acreage,
     fully_maintained (bool),
     stage, stage_entered_at, owner_user_id, vrtsync_map_url,
     annual_value, term_years, renewal_date, source, status, created_at

   acreage is total property size. fully_maintained applies to the whole community. There are no other property profile columns on customers. Do not add irrigation_zones, snow_lots, walk_miles, bed_count, common_areas, or tree_inventory. Those became service layers under amendment A1 and are built in a later slice. Stage is an enum with exactly these nine values: lead, discovery, proposal, signed, mapping, data_load, training, live, churned.
7. Google OAuth sign in. Restrict to a single Google Workspace domain, read from an environment variable. An account outside that domain is rejected with a clear message and no user record is created.
8. On first successful sign in, create a user record with role set to null. A user with a null role can sign in and read. A user with a null role cannot be assigned tasks. There is no password storage, no reset flow, and no invitation system.
9. One endpoint to set a user's role, callable only by a user whose own role is owner.
10. Build the application shell:
    a. Persistent left sidebar, 230px wide, navy, with two groups. Work: Dashboard, Customers, Team To-Do, Projects. Setup: Task Templates, Spec.
    b. Sticky top bar on every screen containing, in this order: screen title, one line context subtitle, search, then primary action aligned trailing.
    c. Content canvas with 22px padding and a 1400px maximum width.
11. Each sidebar item routes to an empty content canvas with the correct screen title in the top bar. No screen content in this slice.
12. A rerunnable seed script that resets and repopulates: four users covering sales, mapping, admin, and owner, plus one user with a null role, and six to eight communities spread across the stages, drawn from the names and figures already in the mockup. Seed data lives in the script. Do not hand enter it.

CONSTRAINTS

Standing constraints, every prompt:

- Plain CSS with custom properties. Do NOT use Tailwind, shadcn, or any
  CSS framework. The stylesheet is ported from vrtsync-crm-mockup.html.
- Do NOT redesign anything. The mockup is the approved design.
- Row vertical padding is 8px. Table cells 10px. Card headers 12px.
- Never use --accent as a text color. Use --accent-ink.
- No em dashes or en dashes anywhere, including comments and UI copy.
- Server is a JSON API only. No server-rendered pages.
- Do not add features, fields, routes, or screens not named in BUILD.

Spec 1.1, platform and stack:

"Platform: responsive web application, installable as a PWA. Not a native app."

"To keep native possible later, the server is an API from day one. No server-rendered pages, no logic that only exists in a template. The web client is one consumer of a JSON API."

| Layer | Choice |
|---|---|
| Client | React with Vite, single page app |
| Server | Express, JSON API only |
| Database | Postgres with Drizzle |
| Styling | Plain CSS ported from the mockup. Not Tailwind. See 4.0 |
| Auth | Google OAuth, restricted to the VRTSync Google Workspace domain |
| Hosting | Replit |

"Auth detail: everyone signs in with their company Google account. No password storage, no reset flow, no invitation system. Domain restriction is the access control. A user record is created on first successful sign-in with role defaulting to null, and Randy assigns the role. A user with a null role can sign in and read but cannot be assigned tasks."

- customers table matches spec 9 as amended by A1: acreage and fully_maintained are present, and no other property profile columns exist on customers.

DO NOT

- Do not use Tailwind, shadcn, Bootstrap, Material, styled-components, CSS modules, or any CSS framework or utility library. Plain CSS files with custom properties.
- Do not write a new stylesheet. Extract the existing one from vrtsync-crm-mockup.html. If that file is missing, stop and say so rather than inventing styles.
- Do not adjust any color, size, spacing, radius, or shadow value while extracting, other than the six cleanups in BUILD item 5.
- Do not create the contacts, notes, tasks, task_templates, template_items, projects, or customer_layers tables. Later slices own them.
- Do not use TypeScript. Plain JavaScript, .js and .jsx.
- Do not generate an OpenAPI or JSON Schema document, and do not add a shared contract package.
- Do not organize this as a monorepo with lib and artifacts directories. One /client, one /server.
- Do not build the Dashboard, Customers list, Customer Record, Team To-Do, Projects, Task Templates, or Spec screens. Empty canvases only.
- Do not add a settings screen, a notifications system, a user profile editor, an admin panel, an onboarding flow, a dark mode toggle, or a landing page.
- Do not add password login, magic links, email invitations, or any auth path other than Google OAuth.
- Do not server render any page. The server returns JSON only.
- Do not add fields to users or customers beyond those listed.
- Do not use em dashes or en dashes in code, comments, commit messages, or interface copy.
- Do not use --accent as a text color anywhere.
- Do not hardcode avatar colors per person.
