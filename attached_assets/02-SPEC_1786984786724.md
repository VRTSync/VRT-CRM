## 1. What This Product Is

An internal CRM for VRTSync, a property maintenance management platform serving HOAs, property managers, and contractors.

It replaces Zoho CRM, which had too many features going unused and was too complex for daily use by a small sales team.

**Three jobs, nothing else:**

1. **Customer tracking.** One record per community, moving along one continuous timeline from first contact through active service. Holds contacts, communication history, to-dos, and documents.
2. **Team to-do list.** Every VRTSync team member's responsibilities in one place, fed largely by templates that fire automatically as customers move through onboarding.
3. **Project management.** A light board for work that does not fit a customer stage or a checklist item.

**Who uses it:** four to six internal people. Sales, Mapping, Admin. No customer-facing access in v1.

**Design consequence:** this is a tool for people who use it every day and will learn it in an afternoon. Favor density and directness over onboarding polish. There is no marketing surface, no empty-state illustration budget, no first-run tour.

**Relationship to the customer-facing portal:** the CRM shares the portal's colors, typefaces, and component vocabulary. It does not share the portal's density. See rule 3.8.

## 1.1 Platform and Stack

**Platform: responsive web application, installable as a PWA. Not a native app.**

The field use case is logging a note and checking off a task from a truck. A responsive web app with an installable manifest covers that. Going native would mean React Native, which cannot consume the ported stylesheet in section 4 at all, which would discard the entire token contract. Native is not ruled out forever, but it is ruled out for v1.

**To keep native possible later, the server is an API from day one.** No server-rendered pages, no logic that only exists in a template. The web client is one consumer of a JSON API. A native client added later is additive work, not a rewrite. This is the single architectural decision that protects the option.

**Stack:**

| Layer | Choice |
|---|---|
| Client | React with Vite, single page app |
| Server | Express, JSON API only |
| Database | Postgres with Drizzle |
| Styling | Plain CSS ported from the mockup. **Not Tailwind.** See 4.0 |
| Auth | Google OAuth, restricted to the VRTSync Google Workspace domain |
| Hosting | Replit |

**Auth detail:** everyone signs in with their company Google account. No password storage, no reset flow, no invitation system. Domain restriction is the access control. A user record is created on first successful sign-in with role defaulting to null, and Randy assigns the role. A user with a null role can sign in and read but cannot be assigned tasks.

**Mobile agility means:** touch targets meet 12's 40px floor, the customer record and Team To-Do are fully usable one-handed, and no screen requires horizontal scrolling on a phone except the two boards, which scroll deliberately.

## 2. Design Principles

**1. Scannable before beautiful.**
The primary user action is a fast scan: what is overdue, what stage is this customer in, who owns this. Anything that slows the scan is a cost.

**2. Density is a feature.**
Desktop-primary software for daily operators. Generous whitespace that pushes content below the fold is a regression, not a refinement.

**3. Status is the loudest thing on screen.**
Overdue, blocked, stale, and current stage carry more visual weight than anything around them. If a user's eye lands anywhere first, it should land on a problem.

**4. One color for progress.**
Teal means forward motion: completed steps, done checkboxes, current stage, live customers, primary actions. It is not used decoratively anywhere.

**5. Property context is what makes this VRTSync and not generic CRM software.**
Unit counts, acreage, irrigation zones, snow areas, bed counts, management company. These are first-class facts, not buried custom fields. A customer record that could belong to any industry has failed.

**6. Quiet chrome, loud content.**
Navigation, headers, and containers recede. Customer names, task titles, and status indicators advance.

## 3. Structural Non-Negotiables

### 3.1 Navigation and shell

- Persistent left sidebar, 230px, navy, with primary navigation. Two groups: **Work** (Dashboard, Customers, Team To-Do, Projects) and **Setup** (Task Templates, Spec).
- The currently open customer appears as an indented sub-item under Customers. See component 6.20.
- Sticky top bar on every screen containing, in order: screen title, one-line context subtitle, search, then primary action aligned trailing.
- **Content canvas is capped at 1400px.** Full-bleed layouts are not permitted for form or list content. The pipeline board and project board are the only exceptions and scroll horizontally.

### 3.2 The pipeline is one continuous line

- Sales stages and onboarding stages render as a **single sequence**, never as two separate visual systems. One record, one progress indicator, Lead through Live.
- Stage order is fixed and displayed left to right: Lead, Discovery, Proposal, Signed, Property Mapping, Data Load, Training, Live.
- On the customer record the stage indicator is a horizontal stepper directly beneath the header, before any tabs. Never collapsed into a dropdown or a single badge.
- Completed, current, and future stages must be distinguishable from each other at a glance. Plus a fourth state for stages left behind by a backward move. See 6.7.

**Backward moves are permitted and must be explained.** A customer may move back any number of stages, not only one. Moving backward requires a typed reason, recorded as a note (see 9 and 10.2). The move is never silent.

**Skipping ahead with an incomplete checklist is also permitted and also requires a reason.** The checklist warns, it does not block. See 7.3 and 14.5.

These are the only two irregular moves, and they carry the same cost: one typed sentence. Everything else in the pipeline is a click.

### 3.3 Status weight ordering

Descending visual weight, in this order:

1. **Overdue** and **Blocked** (alarm)
2. **Due today**
3. **Stale** and **Slow** (warn)
4. **Due this week**
5. **Done** and **Live** (good, quiet)
6. **Neutral metadata**

This ordering is expressed at two levels: the badge on the row, and the card header rule on the container. See note B in 4.6.

### 3.4 Every task row carries four facts

No exceptions, on any screen where tasks appear:

1. A completion control (always leading)
2. The task title
3. Context line: linked customer or "Internal", plus role or assignee, plus source if it came from a template
4. A due or status indicator (always trailing)

### 3.5 The customer record header

In this order. None may move into a tab or secondary panel:

1. Community name
2. Current stage badge
3. Any active alarm state (overdue task, blocked)
4. Fact row: unit count, acreage, management company, assigned manager, internal owner, created date
5. Property profile chips: irrigation zones, snow scope, bed count, tree inventory status
6. Commercial figure: annual value and term
7. Stage stepper

### 3.6 Tabs are for the customer record only

Overview, Communication, Contacts, To-Do, Documents. No other screen introduces tabs. Filtering elsewhere uses inline chip filters.

### 3.7 Communication entries are timeline items, not table rows

A logged call, email, meeting, or site visit renders as a vertical timeline with a type-coded marker, author, timestamp, and full body text. Notes are often three or four sentences of real context. **Never truncate a note body in the customer Communication tab.** Truncation is permitted in the Dashboard activity feed only.

### 3.8 Density floor

Settled values, tightened from the portal's native density to meet the floor:

| Element | Padding |
|---|---|
| Task and list rows | 8px vertical |
| Table cells | 10px |
| Card header | 12px, 48px minimum height |
| Person card header | 10px |
| Stack gap between cards | 14px |

**Floor: 20 task rows fully visible in a 1440x900 viewport on Team To-Do.** Current build measures 22.

If a new screen feels cramped, the answer is fewer elements per row, never more padding. No type size may be reduced to hit the floor.

**The portal and the CRM cannot share a density scale.** Same colors, same type, same components, different padding. If a shared component library is ever built, density must be a variant, not a constant.

### 3.9 Mobile behavior

Desktop-primary, phone-usable. On narrow viewports:

- Sidebar collapses to a horizontal scrolling nav strip.
- Boards and Team To-Do remain functional, single column.
- The customer record and its To-Do tab stay fully readable and tappable. This is the field-use case.
- Search may be hidden below the tablet breakpoint.

## 4. Token Contract

Every color, size, and spacing decision routes through a token. No raw values in component CSS.

### 4.0 The mockup stylesheet is the source

The CSS inside `vrtsync-crm-mockup.html` is not a reference to be reinterpreted. It is the app's stylesheet. Lift it out into real CSS files, fix the items in section 16, and use it.

**Do not rebuild this in Tailwind.** Utility classes will not hold the token contract or the 8px density floor, and every review would become an argument about whether `p-2` is still 8px. Plain CSS with custom properties keeps the spec and the code in the same vocabulary, so a reviewer can compare them directly.

Component class names in the mockup are the component names. `.row`, `.deal`, `.pchip`, `.anchor`, `.k-alarm`, `.stepper`. Keep them.

- Tabular figures for KPI values and unit counts where supported.
- Negative letterspacing on headings only, never below 14px.

### 4.6 Two laws governing color use

**Note A: teal is a fill color, not a text color.**

`--accent` `#25C1AC` scores 2.26:1 against white, well below the 4.5:1 floor in section 12. The darker platform variant `#1da393` reaches only 3.13:1. So the accent is split:

- **`--accent`** for fills, dots, bars, the current stage node, checked checkboxes, progress fill, active borders. Anywhere the color sits behind or beside content rather than being read.
- **`--accent-ink` `#0F766E`** (5.47:1) wherever the accent must be **read**: link text, active filter chip labels, the current stage label, accent badge text.

The same audit applies to the customer-facing portal, where teal-on-white text currently ships below the floor. Tracked separately from this project.

**Note B: card header rules are categorical, not accent.**

Every card carries a gradient rule under its header paired with a small colored dot on the title. This is the strongest brand signal VRTSync has and it stays. It is routed through `--rule-*` tokens rather than `--accent`, so it does not violate principle 4.

| Variant | Use |
|---|---|
| `--rule-neutral` (default, navy) | Any card with no status meaning |
| `--rule-alarm` | Card containing overdue or blocked items |
| `--rule-warn` | Card containing due-today, stale, or slow items, or a stage checklist |
| `--rule-info` | Categorical grouping, pipeline breakdowns |
| `--rule-alt` | Categorical, secondary |
| `--rule-accent` | **Reserved.** Only for a card whose subject is progress itself |

`--rule-accent` is used zero times in the current build. It exists so a genuinely progress-themed card can use it, not as a default.

**Where teal is allowed, in full:** current stage node and filled connectors, checked checkbox, completed stepper node, active filter chip, primary link, progress bar fill, Live and Primary badges, sidebar active-item border, brand mark. Nowhere else.

## 6. Component Anatomy

### 6.1 Badge

- Optional dot or icon, then label text. Single line, never wraps.
- Variants: `neutral`, `accent`, `good`, `alarm`, `warn`, `info`, `alt`, `role`.
- The `role` variant is **outlined** rather than filled, separating role labels from status labels at a glance. This distinction must survive.
- `--fs-2xs`, `--fw-semi`, pill radius. Filled variants use the `-soft` background with the `-ink` text.

### 6.2 Avatar

- Circle, two-character initials, no images in v1.
- Each team member has a fixed color, stable across every screen. A user must be identifiable by color alone in a dense list.
- Sizes: default 26px, large 34px.
- Unassigned uses a neutral gray avatar.

### 6.3 Card

- Header (title, title dot, optional badge, optional trailing actions), gradient rule, then body.
- Body has two modes: padded, or flush for edge-to-edge lists and tables.
- Optional footer band in `--surface-alt` for supporting explanation.
- Header padding 12px, minimum height 48px.

### 6.4 Row

The workhorse. Tasks, checklists, stage counts, contacts, field lists.

```
[ leading control ] [ grow: title / meta line ] [ trailing indicator ]
```

- Leading control: checkbox, avatar, or stage dot. Optional.
- Grow region: title in `--fw-med`, optional meta line in `--fs-xs --muted`.
- Trailing: badge, count, or small button.
- Divider in `--line-2`, none after the last row. Hover uses `--surface-alt`.
- Completed state: title struck through, shifted to `--muted`.
- **Vertical padding 8px.**

### 6.5 Checkbox

- 16px, `--radius-sm`, 1.5px neutral border.
- Checked fills with `--accent-2` and shows a white mark.
- Must be readable from across a room. This is the most-clicked control in the product.

### 6.6 Deal card

Pipeline board and project board.

- Name, one metadata line, optional progress bar, footer row.
- Footer: owner avatar, then a status badge or short note.
- Progress bar appears only on cards at or past Signed, showing onboarding completion.
- Customer metadata line is always `unit count + management company`. Project metadata is a one-line description.
- Hover raises with `--shadow-md`.

### 6.7 Stepper

- Horizontal, scrollable on narrow viewports, never collapsed.
- **Four node states:**

| State | Meaning | Treatment |
|---|---|---|
| `done` | Completed, behind the current stage, normal forward progress | Accent fill, check mark |
| `current` | Where the customer is now | Accent ring, focus emphasis, `--accent-ink` label |
| `future` | Not yet reached | Neutral outline, muted label |
| `behind` | Was completed, then the customer moved backward past it | Outlined in `--warn`, muted fill, warn label |

The `behind` state exists because a backward move leaves completed nodes sitting ahead of the current node, which reads as broken without it. A node in `behind` state is still ahead in sequence but no longer counts as progress.

- Connectors filled to the current stage, unfilled after. Connectors past a backward move render unfilled.
- Optional date beneath each completed node.
- Hovering a `behind` node surfaces the reason from the stage change note.

### 6.8 Timeline

Communication history, activity feeds, project notes.

- Vertical rule with markers offset onto it.
- Marker type-coded by entry kind: call, email, meeting, site visit, note, system.
- Item header: author, type badge, timestamp trailing. Body at `--fs-sm` in `--ink-2`.
- Body wraps freely. See rule 3.7.

### 6.9 Filter chip

- Pill, outlined by default. Active state uses `--accent-soft` background with `--accent-ink` text.
- Grouped horizontally, one active per group.

### 6.10 Note composer

Top of the customer Overview tab.

- Text area with placeholder, then an action row.
- Action row: kind chips (Call, Email, Meeting, Site visit, Note), then save aligned trailing.
- One to two lines collapsed, expands on focus.

### 6.11 KPI tile

- Uppercase label, large value, small delta line.
- The only place `--fs-display` appears alongside the anchor band.
- **Status variants** carry a 3px bottom border and a faint top-left gradient tint in the status color. The value alone is too quiet at the top of a dense screen. This is not a large status fill and does not violate 4.1.

### 6.12 Template row

```
[ sequence ] [ task title (grow) ] [ role badge ] [ due offset ]
```

Fixed widths on the trailing two so the column reads vertically.

### 6.13 Callout

- Informational only, `--info-soft` background, `--info` left border, `--info-ink` text.
- Never used for warnings or errors.
- Keep to one rendered line where it sits above dense content.

### 6.14 Anchor band

Navy gradient panel at the top of Customers. Contains an eyebrow label, a headline figure, a segmented progress bar with legend, and right-aligned stat columns.

The portal's signature summary device and the strongest brand carrier in the product. Answers "state of the whole book of business" on a screen that is otherwise a board, which a KPI strip does not do.

Uses `--shadow-md`. Figures in Outfit.

### 6.15 Card kind (`k-*`)

A modifier on Card that sets the header rule and title dot together. Six kinds: `k-navy`, `k-alarm`, `k-warn`, `k-info`, `k-alt`, `k-accent`.

Makes the status weight ordering in rule 3.3 visible at the container level, so a card full of overdue work reads as a problem before a single row is scanned.

### 6.16 Property chip (`pchip`)

Outlined chip with a color square, a label, and a bold value. Used for the property profile row required by rule 3.5 item 5.

Badge is the wrong component here because these are label-plus-value pairs, not statuses.

### 6.17 Fact row

Horizontal run of uppercase micro-label over value. Used for rule 3.5 item 4 and repeated on project detail.

### 6.18 Sidebar sub-item

Indented nav row for the currently open customer. Provides a route back to the record without pretending it is a top-level destination.

## 7. Screen Specifications

### 7.1 Dashboard

**Purpose:** answer "what needs me today" in under five seconds.

1. **KPI strip**, four tiles: Active Pipeline, Onboarding, Live Communities, My Open Tasks. The fourth takes the alarm variant when overdue tasks exist.
2. **Two-column body** (`g-2-1`):
   - Main: My To-Do card (`k-alarm` when overdue), then Recent Activity timeline.
   - Rail: Pipeline by Stage, Needs Attention (`k-warn`), Team Load.

**My To-Do:** current user's open tasks, overdue first then due date ascending. Today's completed tasks remain visible at the bottom in a completed state.

**Recent Activity:** cross-customer timeline, most recent first, roughly ten entries. Body may truncate to two lines here only.

**Needs Attention:** derived at read time, not stored:
- **Stale:** newest note over 21 days old and stage in (lead, discovery, proposal)
- **Blocked:** any open task on the customer has status blocked
- **Slow:** `stage_entered_at` over 30 days ago and stage is not live

**Team Load:** every active user, avatar, name, role, open task count, sorted descending.

### 7.2 Customers

1. **Anchor band** summarizing the book of business: total communities, segmented pipeline bar with legend, and stat columns.
2. Top bar with a Board / List toggle and a New Customer action.
3. Callout describing the single continuous pipeline and the Signed trigger.
4. **Board:** one column per stage in fixed order. Column header shows stage dot, name, count. Cards drag between columns. The Live column caps visible cards with an overflow indicator.
5. **List:** table with Community, Management Co., Units, Stage, Owner, Last Contact, Next Step. Sortable. Row click opens the record.

Board and List show the same data. The toggle is a per-user preference.

### 7.3 Customer Record

**Header:** exactly as rule 3.5, followed by the stepper.

**Overview** (default), two columns:
- Main: note composer, then the stage checklist for the current stage (`k-warn`).
- Rail: Key Contacts, Contractors on Site.

The stage checklist shows checkbox, title, assignee and due date where set, and a role or status badge.

**The checklist warns, it does not block.** Below it, a line reading: "You can advance with items still open. You will be asked why, and the open items follow the customer forward."

Incomplete items are never deleted on advancing. They stay open, stay assigned, and keep appearing on their owner's Team To-Do. The debt stays visible.

**Communication.** Filter chips (All, Calls, Emails, Meetings, Site visits) with entry count trailing. Full timeline, newest first, untruncated.

**Contacts.** Table: Name, Role, Organization, Email, Phone, Primary. Contractor contacts included and marked with a badge rather than split into a separate table.

**To-Do.** Two sections, Open and Completed, each with a count. Open has an inline add action. Rows follow rule 3.4.

**Documents.** Table: File, Type, Added by, Date. Type is categorical: Proposal, Photos, Contractor, Property, Other. Footnote states that documents follow the customer into the VRTSync platform after onboarding.

### 7.4 Team To-Do

1. Callout naming the three task sources: templates fired by stage change, meeting action items, manual entries. One rendered line.
2. Filter bar, two chip groups separated by a gap: role filters (All roles, Sales, Mapping, Admin) and view filters (Overdue only, This week, Unassigned).
3. Two-column grid of person cards. Header: avatar, name, role, count summary showing open and overdue. Then task rows.
4. Unassigned card, always last, with an Assign action per row.

## 8. Interaction and State Rules

**States every interactive element needs:** default, hover, active, focus visible, disabled. Focus rings must be visible against both the light canvas and the navy sidebar.

**Empty states.** Text only, one line, plus an action where applicable. No illustrations, no large icons.
- No tasks: "Nothing open. Add a task or wait for the next stage change."
- No communication: "No contact logged yet. Use the box above to log the first call or meeting."
- No documents: "No files yet."

**Loading.** Skeleton rows matching the shape of the content that replaces them. No full-screen spinners.

**Destructive actions.** Only three exist: delete a customer, delete a task, delete a template row. Each requires confirmation. Nothing else is destructive.

**Drag and drop.**
- Pipeline cards drag between stages, project cards between statuses.
- **Forward, checklist complete:** confirmation showing how many tasks will be created and to whom, then commit.
- **Forward, checklist incomplete:** the same confirmation, plus a required reason field, plus a line naming how many items are being carried forward still open.
- **Backward, any distance:** a required reason field, plus a warning naming how many open tasks will be deleted and how many completed tasks will be kept. Then commit. See 10.2.
- The reason field is a single text input. No dropdown of canned reasons. People write what happened or they write nothing useful.

**Optimistic updates.** Checking a task, moving a card, and saving a note update immediately and reconcile in the background. Failures surface inline on the affected element, not as a global toast.

## 10. Automation Logic

Stage change is the only automation in v1. Everything below happens in one transaction.

### 10.1 Any stage change

1. Write one note with `kind = system`, `from_stage` and `to_stage` set, and `body` holding either the typed reason (backward move or skip-ahead) or a generated sentence (ordinary forward move).
2. Set `stage_entered_at` to now.
3. If the move is backward, run 10.2, then stop. Templates do not fire on backward moves.
4. Look up an active template whose `trigger_stage` matches the new stage.
5. **For each template item that does not already have a task on this customer, in any status, create one.** Set `due_date = today + due_offset_days`, `source = template`, `template_item_id` set.
6. Resolve the assignee in this order:
   - The customer owner, if they hold the item's role
   - The sole active holder of that role
   - Otherwise leave `assignee_user_id` null, landing in Unassigned

**Why step 5 reads that way.** The dedupe check on `template_item_id` is what makes re-entering a stage safe. A customer who moves back and then forward again gets the deleted tasks recreated with fresh due dates, while tasks already completed are correctly skipped. This replaces the older rule that blocked a template from firing twice, and it removes the need to track stage history for automation purposes.

### 10.2 Backward moves

A move is backward when `to_stage` sits earlier in the fixed stage order than `from_stage`, at any distance.

1. **Delete open tasks** belonging to the stage being abandoned, meaning tasks whose `template_item_id` maps to the template for `from_stage` and whose status is `open` or `blocked`.
2. **Keep completed tasks.** They are the record of work actually done and they remain in the customer's To-Do history.
3. Manually created tasks are never deleted, whatever stage they were created during. Only template-sourced tasks are in scope.
4. Mark the abandoned stages as `behind` for stepper rendering. This is derived from the note history, not stored.

Deleting an open task destroys no history, because open means nobody did the work. The reason note carries the why.

**Known consequence:** if someone manually deletes a template task and the customer later re-enters that stage, the task returns. This is intended.

## 11. Content and Voice

The interface should read like it was written by someone who understands HOA operations, not by a software company.

**Do:**
- Use the words the business uses: community, board, management company, property walk, as-builts, irrigation zones, snow map, common area.
- Write button labels as verbs: Log Note, Add Task, Assign, Open Property Map.
- Write empty states and callouts in plain sentences.

**Do not:**
- Use generic CRM vocabulary where a specific word exists. It is a **community**, not an account. It is a **board vote**, not a close date.
- Use exclamation marks, congratulatory messaging, or celebratory states.
- **Use em dashes or en dashes anywhere in interface copy.**
- Use "seamless", "powerful", "robust", or "solution".

**Fixed labels:**

| Concept | Label |
|---|---|
| The customer entity | Customer (nav), Community (in prose) |
| A logged interaction | Note |
| The task list | To-Do |
| The pipeline position | Stage |
| A person at the customer | Contact |

## 12. Accessibility Floor

- Body text contrast at least 4.5:1. Metadata at `--fs-xs` and smaller must clear 4.5:1, not 3:1.
- **Teal never appears as text.** Use `--accent-ink`. See note A.
- Status is never communicated by color alone. Every status badge carries text. Every stage dot has a stage name beside it.
- All interactive elements keyboard reachable with a visible focus indicator on both light and navy backgrounds.
- Drag and drop has a keyboard equivalent: a stage selector on the customer record, a status selector on the project card.
- Minimum touch target 40px below the tablet breakpoint.

## 14. Decisions and Open Questions

**14.1 Moving a customer backward: settled.** Open template tasks from the abandoned stage are deleted, completed ones are kept, and the move requires a typed reason recorded as a note. See 3.2, 8, 10.2. Suspension was considered and rejected as more machinery than the problem deserves.

**14.2 Open.** Does an annually renewing community need a renewal record per year, or is one date on the customer sufficient? Not blocking before slice 7.

**14.3 Open.** Should contractors eventually get a login to see their own tasks, or remain read-only records? Out of scope for v1 either way.

**14.4 Open.** How much of the property profile belongs in the CRM versus living only in the VRTSync platform? Current answer is the six fields in 9. Revisit after the platform integration is real.

**14.5 Stage checklist: settled. It warns, it does not block.** Advancing with open items is allowed and requires a typed reason. Open items follow the customer forward rather than disappearing. Reasoning: hard gates in small teams do not produce compliance, they produce people checking boxes to get past the gate, which makes the data worse than no checklist. See 7.3.

## 17. Quick Reference

For anyone adding a screen without this document open:

1. **Navy is chrome and ink. Teal is progress. Everything else is status.** A color doing none of those three jobs should not be there.
2. **Every card gets a header rule.** Default navy. Color it only when the contents carry status.
3. **Headings are Outfit, everything else is Inter.**
4. **Status always carries text**, never color alone.
5. **Row padding is 8px.** Cramped means fewer elements per row, not more padding.
6. **Accent text uses `--accent-ink`.** Never `--accent`.
7. **`--fs-display` appears only in KPI values and the anchor band.**
8. **Uppercase with letterspacing** is for table headers, board column names, KPI labels, and fact row micro-labels. Never buttons, never body.
