# 01 BRIEF: Decisions and Why

The spec records conclusions. This file records reasoning. Read it once per session so you do not reopen settled ground.

---

## Why this exists

VRTSync ran on Zoho CRM. Most of its features went unused and it was too complex for the salesman to use daily. The replacement is deliberately small: three jobs, and a hard bias toward cutting anything that is not one of them.

The failure mode to avoid is not "missing a feature." It is rebuilding Zoho.

---

## Settled decisions

**One continuous pipeline, not two.** Sales stages and onboarding stages sit on the same timeline. A community keeps one record from first contact through active service. Rejected: separate sales and onboarding pipelines with a handoff, because the handoff is where knowledge gets dropped, and preserving knowledge is the whole point of the parent product.

**Tasks assign to roles, not people.** Templates specify Sales, Mapping, or Admin. The system resolves to a person at fire time. Rejected: hard-assigning to named individuals, which breaks the moment someone leaves or the team grows.

**Manual note logging. No email sync.** Every call, meeting, and email is typed in by hand. Accepted cost: people will forget to log things. Accepted reason: email sync is a large build with an OAuth surface, and the team is six people who can be told to log their calls. Revisit if it actually fails in practice.

**No Zoho import.** Active deals get re-entered by hand. Rejected: full CSV migration, which drags legacy mess into a system whose entire purpose is being cleaner than what it replaced.

**Responsive web, not native.** The field case is logging a note from a truck, which a PWA handles. Native would mean React Native, which cannot use the ported stylesheet at all, which would discard the token contract. The server is a JSON API from day one so a native client stays possible later without a rewrite.

**Plain CSS, not Tailwind.** The mockup's stylesheet becomes the app's stylesheet. Tailwind would not hold the 8px density floor or the token contract, and every review would become an argument about whether a utility class still means what the spec says. Keeping spec and code in the same vocabulary is worth more than the agent's familiarity with Tailwind.

**Google auth, domain restricted.** Company Google accounts only. No passwords, no invitations, no reset flow. Role is assigned by Randy after first sign-in.

**Backward stage moves delete open tasks and keep completed ones.** Suspension was designed, then rejected as more machinery than the problem deserves. An open task contains no record of work, so deleting it destroys nothing. The typed reason note carries the history.

This forced a better automation rule. The old rule blocked a template from firing twice, which would have made deleted tasks unrecoverable on re-entry. The replacement creates a task for any template item that does not already have one, in any status. That single dedupe check handles first fire and re-entry both, and removed the need to track stage history for automation at all.

**The stage checklist warns, it does not block.** Hard gates in small teams do not produce compliance. They produce people checking boxes to get past the gate, which makes the data worse than having no checklist. Advancing with open items costs a typed reason, and the open items follow the customer forward so the debt stays visible.

## Design decisions worth not relitigating

**Teal is a fill, never text.** `#25C1AC` scores 2.26:1 on white, well under the 4.5:1 floor. `--accent-ink` `#0F766E` exists for anything that has to be read. This came out of the design pass as a real accessibility catch, and the same problem exists in the customer-facing portal, tracked separately.

**Card header rules are categorical, default navy.** The gradient rule under a card header is the strongest brand signal VRTSync has, so it stays, but it routes through `--rule-*` tokens rather than the accent so it does not turn teal into decoration. `--rule-accent` is reserved and currently unused.

**Density is a feature, not an oversight.** The customer-facing portal is looser. Applied here as-is it fit 17 task rows and missed the floor. Padding was tightened to 8px rows and 10px cells to reach 22. The portal and the CRM cannot share a density scale, and if a shared component library is ever built, density has to be a variant.

## Still open

None of these block the current slice. Do not invent answers.

- Does an annually renewing community need a renewal record per year, or is one date enough? Needed before slice 7.
- Should contractors eventually get a login? Out of scope for v1 either way.
- How much property profile belongs in the CRM versus the VRTSync platform? Current answer is the six fields in spec section 9.
